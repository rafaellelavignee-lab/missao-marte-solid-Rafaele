O que é este projeto?

Peguei um jogo em Java que tinha tudo misturado em poucas classes (monolítico) e refatorei usando os princípios SOLID. O código original funcionava bem, mas era meio bagunçado para manutenção.

Agora está organizado em 3 camadas bem definidas: Model, Service e Repository.

Princípios SOLID aplicados

Single Responsibility (SRP)

Cada classe tem uma única responsabilidade:

  • GameService: lógica do jogo
  • GameRenderer: apenas renderiza o mapa
  • RankingService: gerencia o ranking
  • JsonRankingRepository: salva/carrega dados

Open/Closed (OCP)

Posso adicionar novos tipos sem quebrar o código existente:

// Para criar novo passageiro:
public class Medico extends Passageiro {
    @Override
    public int getPontuacao() {
        return 25;
    }
}
// Pronto! GameService continua funcionando

Liskov Substitution (LSP)

Subclasses podem ser usadas no lugar da classe base sem problemas:

  • Asteroide e Inimigo funcionam igual como Perigo
  • Professor, Engenheiro, Astronauta funcionam igual como Passageiro

Interface Segregation (ISP)

Interfaces pequenas e focadas:

Posicionavel (getX, getY)
Movel extends Posicionavel (mover)
Perigo extends Posicionavel (colideCom)

Dependency Inversion (DIP)

GameService depende de abstrações, não de implementações concretas:

// Injeção de dependência
GameService(GameRenderer renderer, 
            RankingService rankingService)

Isso permite trocar a implementação sem alterar GameService.

Como compilar e executar

Código original:

cd solid-tutorial
javac -d bin src/exercicio10/*.java
java -cp bin exercicio10.Main

Código refatorado:

javac -d bin src/solidexercicio10/*.java src/solidexercicio10/service/*.java src/solidexercicio10/repository/*.java
java -cp bin solidexercicio10.Main
✓ Ambas as versões compilam e funcionam sem erros

Dificuldades que enfrentei

1. Encoding BOM no PowerShell

Quando criava arquivos Java no PowerShell, aparecia o erro:

error: illegal character: '\ufeff'

Solução: Usar -Encoding ASCII ao invés de UTF8

Out-File -Encoding ASCII  # Correto!

2. Arquivos conflitantes

Tinha versões antigas das classes causando conflitos na compilação.

Solução: Limpar a pasta solidexercicio10 e recriar do zero.

3. PlantUML com caracteres especiais

Quando colocava caracteres especiais (✓, ❌, etc) no diagrama, queimava no PlantUML online.

Solução: Usar apenas ASCII e deixar o diagrama simples.

Decisões com as quais CONCORDO

1. Separação em 3 camadas (Model, Service, Repository)

Por quê: Deixa o código muito mais organizado. Cada parte tem um propósito claro.

Benefício: Quando preciso alterar como os dados são salvos (de JSON para banco de dados), só mexo na camada Repository. O resto do código não precisa mudar!

2. Usar interfaces para abstrair comportamentos

Por quê: Ao invés de trabalhar com classes específicas, trabalho com interfaces.

Benefício: Posso adicionar novos tipos (novo passageiro, novo perigo) sem mexer no GameService. O código fica aberto para extensão, fechado para modificação.

3. Injeção de dependência

Por quê: GameService recebe seus colaboradores (renderer, rankingService) por parâmetro.

Benefício: Fica muito fácil trocar as implementações. Para testar, posso passar versões fake. Para usar em produção, passo as reais.

Decisões com as quais NÃO CONCORDO (ou faria diferente)

1. Persistência apenas em JSON

Problema: Se o arquivo JSON ficar corrompido, perde todos os dados.

O que faria: Usar um banco de dados (SQLite, H2Database) com fallback para JSON.

Impacto: Para um projeto universitário, JSON funciona. Mas em produção, seria importante.

2. GameRenderer só faz System.out.println()

Problema: Se no futuro quisermos uma interface gráfica, fica complicado.

O que faria: Criar uma interface Renderer com diferentes implementações (Console, GUI, Web).

Impacto: Média prioridade. O projeto atual funciona bem assim.

O que aprendi

  • SOLID não é apenas teoria, na prática torna o código muito mais limpo
  • Separar em camadas (Model, Service, Repository) realmente funciona
  • Interfaces pequenas são melhor que interfaces gigantes
  • Injeção de dependência torna os testes muito mais fáceis
  • Encoding pode quebrar compilação Java (cuidado com BOM!)
